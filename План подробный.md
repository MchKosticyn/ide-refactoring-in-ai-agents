**Название:** Использование инструментов рефакторинга IDE в ИИ-агентах
**Формат:** 40–45 минут + вопросы
**Аудитория:** смешанная; бэкенд/фронтенд-разработчики и тестировщики, часть не пользуется агентами

Формат записи для каждого пункта: время → что на слайде → что говорим → зачем → материалы.

Статусы: ✅ согласовано · 🔲 в работе · ⬜ не начато

**Решение по структуре (2026-09-29):** доклад строится на одном реальном кейсе — detekt, PR #7873 (`compileAndLint` → `lint`). Порядок: рамка (определение, по чему судим) → зачем это QA → кейс → человек в IDE → термины → Claude Code текстом → текстовый подход → «пугалка» → Veai → LSP → движок IDE → таблица → MCP → советы → summary. Синтетический кейс `getName → getDisplayName`, Spring XML и пример `j → i` убраны. Часть «проектирование тулов» — один backup-слайд после «Спасибо».

**Метрики (2026-09-29):** у каждого демо справа от видео — стоимость + токены, время, ходы, стартовый контекст. У человека — время и стоимость (часовая ставка × время). Значения — по факту записи; в плане — поля.

**Единые правила:** разбор каждого прохода — три аспекта без вердикта в названии: «Найдены все места / Правки только по делу / Поведение сохранено»; красный только если плохо, зелёный если хорошо. У каждого подхода один слайд «Плюсы и минусы». Заголовки короткие. Слайд «План доклада» с прогрессом — на границах глав. Про LSP — только на уровне протокола; поведение конкретного сервера — как иллюстрация с пометкой «например».

**Тайминг (оценка):** ≈ 48 мин с п. 3. Резерв на срезание: п. 9 (1 мин), п. 14 MCP до 1 мин, «атомарность» в 1 слайд-строку, видео человека до 1,5 мин.

## 2. Рамка: по чему судим ⬜

**Время:** 2 мин, один слайд.

**Слайд:** определение сверху; две карточки подзадач; внизу — три аспекта разбора и метрики.
- Верх: «Рефакторинг — изменение структуры кода без изменения поведения программы».
- Карточка 1 «Найти все места» — полнота. Пример: «78 вызовов × 97 % = 2 пропуска».
- Карточка 2 «Применить» — корректность: правка не должна менять, к какому методу привязан вызов, и не должна задевать чужое.
- Низ: аспекты разбора — «Найдены все места / Правки только по делу / Поведение сохранено»; метрики — время, стоимость, ходы, токены, стартовый контекст.

**Говорим:**
- Определение. Рефакторинг — не поиск и не генерация, а преобразование с гарантией.
- Две подзадачи; разные инструменты сильны в разных.
- По чему будем судить каждый проход — три аспекта и метрики. Одни и те же для человека и для агентов.

**Не обсуждаем:** RAG; «зачем агент, если Shift+F6» — в Q&A.

**Зачем:** каркас для всех разборов. Стоит первым: даёт язык, которым дальше говорим про поводы (п. 3) и про кейс (п. 4).

## 3. Зачем это QA ⬜

**Время:** 2 мин, один слайд.

**Слайд:** три карточки «поводы» и строка «почему больно».
- Поводы (примеры с митинга оргкомитета): миграция тестового фреймворка — Selenium → Playwright, JUnit 4 → 5; наведение структуры — spaghetti → PageObject, одна большая фикстура → композиция; изменение тестового API проекта — хелперы, DSL, базовые классы; аудит и переписывание по его итогам.
- Почему больно: сотни и тысячи мест; часть связей не выглядит как вызов; зелёные тесты — не доказательство, что поведение то же (сам рефакторинг меняет тестовый код).
- Строка: «Хочется отдать агенту. Первый опыт обычно разочаровывает — разберём, почему, на реальном кейсе».

**Говорим:**
- Рефакторинг тестового кода — регулярная работа QA, не разовая. Примеры — из практики программного комитета.
- Ручной способ есть и работает (IDE), но долгий; агент обещает быстрее — проверим, чем это оборачивается.
- Переход к кейсу: берём небольшой реальный, чтобы посчитать, а не рассуждать.

**Зачем:** «продать проблему» до решений — прямое замечание оргкомитета. Без этого слайда зал не понимает, зачем ему доклад.

## 4. Кейс ⬜

**Время:** 3 мин, два слайда.

**Слайд 1 — проект и задача.**
- detekt — статический анализатор Kotlin. `detekt-test` — тестовый DSL, которым авторы правил пишут спеки.
- Две функции с одинаковыми параметрами, рядом в одном файле (`RuleExtensions.kt`, строки 21–43):
  ```kotlin
  fun Rule.compileAndLint(content, compilerResources) // компилирует сниппет (под флагом CI), потом линтит
  fun Rule.lint(content, compilerResources)           // только линтит — для сниппетов, которые не компилируются
  ```
- Задача автора PR (цитата из описания, 2025-02): «rename `compileAndLint` to `lint` so the function is always the same AND if you … doesn't want to compile the snippet … you can set `.lint(code, compile = false)`».

**Слайд 2 — масштаб.** Четыре числа: 1428 вызовов `compileAndLint` в 131 файле; 78 вызовов старого `lint` в 17 файлах — им нужен `compile = false`; не трогать: перегрузку `lint(ktFile)` (36) и одноимённый `FormattingRule.lint` в другом модуле (66). Подпись: «Задача — переименование. Всё интересное — в этих 78».

**Говорим:**
- Реальный проект, реальный PR, ничего не придумано. Проект открытый — можно повторить.
- Почему это рефакторинг тестового кода: меняется API, которым пишут тесты; поведение тестов должно остаться прежним.
- Ловушки не называем — они всплывут в разборах. Только цифры.

**Зачем:** зал видит задачу до того, как увидит, как её решают. Все проходы дальше — на ней. Связка с п. 3 — фразой: «тестовый DSL вашего проекта устроен так же: пара хелперов, сотни вызовов, и правило, которое держится на дисциплине».

**Материалы:** `demo-detekt.md`, https://github.com/detekt/detekt/pull/7873, pre-PR коммит `a4ec32a2`.

## 7. Демо 1: Claude Code, текстовые правки ⬜

- Промах — там, где имя не выглядит как вызов метода. Grep ищет строку, вызов без точки — не строка `.lint(`.

## 8. Текстовый подход ⬜

**Время:** 4 мин, три слайда. Содержание прежнее, примеры — из detekt.

**Слайд 1 — что это.** Цикл: задача → поиск по тексту → чтение → правка текстом → diff. Код для агента — строки; символов не существует. Три механизма правки: скрипт/regex по файлам; тул «правка фрагмента»; перезапись файла.

**Слайд 2 — плюсы и минусы.** Плюсы: ноль настройки; любой язык; работает на некомпилирующемся коде. Минусы: имя ≠ символ (одноимённый `FormattingRule.lint`, комментарий); символ ≠ имя (вызов без точки, неявный receiver); шум — частые идентификаторы.

**Слайд 3 — где ломается.** Полнота: пропуски (символ без ожидаемой строки) и ложные попадания (строка без символа). Корректность: правка не знает, что меняет — символ, строку или комментарий; N мест — N независимых операций; «прошло» всегда, даже если заменило не то.

**Говорим:** три плюса честно — последний вернётся в таблице как ниша. Оба провала — из одной причины: подстрока не равна символу. Пример без точки — из демо.

Вывод-переход (оргкомитет: после каждого подхода — почему пошли дальше): «Промах молчаливый, сборка зелёная, 53 хода и $4 — нужен инструмент, который видит символы, а не строки».

**Зачем:** первый подход проваливает обе подзадачи по-разному; контраст для LSP (символы есть) и движка (проверка до правки).

**Убрано:** цифра про шум из GrepRAG (без синтетического кейса не к чему привязать); Kotlin-свойство `user.name`.

## 9. Почему агенты правят текстом ⬜

**Время:** 1 мин, один слайд.

**Слайд:** три цитаты с источниками, одна строка контраста.
- Codex CLI, системный промпт: «prefer using `rg` … Do not use apply_patch … when scripting is more efficient (such as search and replacing a string across a codebase)».
- Claude Code, режим bypass/auto: «make file changes with `sed`, heredocs, or short scripts, rather than using the dedicated Read, Edit, or Write tools» (по issues anthropics/claude-code #88475, #90599; версии 2.1.228–2.1.251). Документация: на macOS/Linux «leaves Glob and Grep out of the default tool set … searches with `find` and `grep` through the Bash tool».
- OpenCode, тул Edit (при наличии LSP для диагностики): «Use `replaceAll` … if you want to rename a variable».
- Строка контраста: LSP/IDE-rename есть у Copilot CLI, JetBrains Junie, Serena.
- Строка про модели: «Смещение есть и у моделей: на бенчмарке Veai доля правильных вызовов тулов у Claude ниже, чем у других моделей, примерно на 10 п.п.» — цифру согласовать с компанией.

**Говорим:** это в первую очередь инструкция агента, а не выбор модели: та же модель внутри другого агента тулы вызывает (демо 2–3 — на той же модели, что демо 1). Смещение у моделей тоже есть, но измеримое и небольшое — говорим цифру, не прячем. Единственный инструмент правки у терминальных агентов — замена строки или патч; где LSP подключён — он read-only или для диагностики. Отсюда переход: дадим агенту другие инструменты.

**Не утверждать:** что bypass-блок опубликован Anthropic (только issues); что он действует вне bypass/auto; промпты Cursor — утечка, не цитировать; что модели «переобучены» на текст — у нас только доля вызовов на бенчмарке, причины не знаем. Отдельного слайда «Anthropic vs OpenAI» не делать.

**Зачем:** объясняет, почему текст — по умолчанию, и мотивирует остальную часть.

## 11. Демо 2: LSP ⬜

**Время:** 7 мин: видео 3 + что это 1 + разбор 1 + ограничения 2.

Перед видео — одна фраза устно, без слайда: «LSP — сервер, который понимает язык; агент спрашивает его, где символ используется, и просит переименовать». Подробности — после видео.

**Слайд 1 — видео.** Veai, LSP включён, рефакторинг выключен. Справа — метрики (стоимость + токены, время, ходы, стартовый контекст). Колонка действий: агент запрашивает references по символу → получает список → правит текстом по списку → rename по протоколу (если использует). Титры: сервер (JetBrains Kotlin LSP), версия, дата.

**Слайд 2 — что такое LSP.** Определение: протокол между редактором/агентом и сервером языка; отдельный процесс понимает язык, клиент спрашивает по стандарту; один сервер — один язык. Схема: запрос «переименуй здесь» → сервер → список текстовых правок → применяет клиент. Что даёт: определение, использования, переименование.

**Слайд 3 — разбор.** По факту записи. Ожидание: найдены все места — да (references на старом `lint` — 99 ссылок, включая оба вызова без точки); правки только по делу — зависит от того, правит ли агент по списку текстом; поведение сохранено — зависит. Rename `compileAndLint → lint` через протокол — отказ: «function already declared».

**Слайд 4 — ограничения протокола.** Четыре карточки; каждая — тезис на уровне спецификации (источники — `research/lsp-limitations.md`). Порядок — по весу для агента:
1. **Операции без параметров.** В протоколе один семантический рефакторинг — rename (позиция + имя). Остальное — `codeAction`, которые сервер предлагает сам, клиент выбирает из готовых; передать «в какой модуль», «на какую сигнатуру» нечем. Change Signature, Move, Inline, Safe Delete — названия категорий для меню, не операции.
2. **Модель и файлы в разных процессах.** Сервер владеет моделью, клиент — файлами; о правках агента сервер узнаёт через уведомления. Сигнала «индекс актуален» нет; полноту `references` на момент вызова протокол не обещает.
3. **Один сервер — один язык.** Ссылки из другого языка и из конфигурации (XML, properties) недоступны; механизма композиции серверов в протоколе нет.
4. **Конфликты — на усмотрение сервера.** Протокол не обязывает о них сообщать и не задаёт форму: один сервер вернёт ошибку с объяснением, другой применит молча, третий пометит правки (`ChangeAnnotation`). После отказа продолжить нечем — параметра «применить несмотря на конфликт» нет.
Строка под карточками: «Автор тула не может обещать модели то, что протокол не гарантирует».

**Говорим:**
- Первый подход, где есть символ: полнота в пределах языка появляется. Оба вызова без точки найдены.
- Rename отказал — это лучше, чем молча применить. Текст ошибки модель прочитать может; проблема не в форме, а в том, что это выбор сервера, а не правило протокола, и продолжить после отказа нечем.
- Поиск у LSP — по символам, применение — текстовое, клиентом (атомарность агент-клиент может обеспечить сам; это не ограничение протокола). По полноте в одном языке ближе к движку; операции — только rename.
- Оговорка одной фразой: что сервер делает внутри ограничений — своё у каждого (clangd и gopls отказывают, rust-analyzer помечает правку, JetBrains Kotlin LSP отказал нам); говорим про протокол. Наблюдение «2 → 79 ссылок» — иллюстрация, не тезис.
- Вывод-переход (оргкомитет: после каждого подхода — почему пошли дальше): «Символы видит, оба вызова без точки нашёл. Но операция одна — rename, конфликт — как повезёт с сервером, один язык. Нужен движок».

**Зачем:** LSP — то, что зал считает уже решением. Показываем: полнота в одном языке есть; операций с параметрами нет, актуальность модели не гарантирована, конфликты — как повезёт с сервером.

**Материалы:** `research/lsp-limitations.md` (спецификация 3.17/3.18, issues мейнтейнеров; разделы «Что можно говорить со сцены» и «Что нельзя утверждать»); `research/repro-2026-09-29.md` (references 2 → 79; отказ rename). `notes-lsp-vs-psi.md` раздел 1 — пересмотреть по тем же правилам.

## Q&A: заготовки ответов

### «Почему не сделать LSP как PSI?»

**Короткий ответ:** PSI — не протокол, а общая модель кода в одном процессе. LSP по замыслу — один сервер на один язык, изолированные процессы, обмен текстовыми правками. Чтобы сервер одного языка увидел ссылки из другого, нужен либо один процесс с общей моделью — это и есть IDE, — либо протокол координации серверов, которого в LSP нет.

**Развёрнуто:** нет параметров у операций (только rename); модель и файлы в разных процессах без сигнала актуальности; клиент не объединяет ответы серверов по символам; сообщать о конфликтах протокол не обязывает. **Оговорка:** спецификация не запрещает один сервер на много языков — но тогда это IDE в другой упаковке; JetBrains Kotlin LSP собран на ядре IntelliJ, и именно поэтому он отказал в rename в занятое имя.

### «Зачем агент, если есть Shift+F6?»

Ценность не в одном переименовании, а когда рефакторинг нужно придумать, когда их двадцать связанных, или когда он часть большой задачи. В кейсе: человек делает три операции и сливает тела руками; агент делает то же по описанию PR.

### «А эмбеддинги / RAG?»

Вне рамок. Для поиска повода — да; для полноты — нет: ранжирование вероятных, а не перечисление всех.

### «Текстовый агент промахнулся на двух вызовах — это же мелочь?»

Мелочь по объёму, не по типу: промах молчаливый, сборка и тесты зелёные. Найти его можно, только зная, где искать. Реальный PR-автор проставил `compile = false` в этих местах руками.

### «А если модель не хочет пользоваться тулом?»

Два рычага. Первый — агент: системные промпты терминальных агентов предписывают grep/sed (п. 9), и та же модель в другом агенте тулы берёт. Второй — модель: смещение есть и измеримо (бенчмарк Veai: у Claude доля правильных вызовов ниже примерно на 10 п.п.). Что помогает: описание тула — это промпт, когда и зачем его вызывать; указание в тексте задачи работает (в наших прогонах 5 из 5), в системном промпте — нет (0 из 5). Если на записи модель тул не взяла — говорим цифры, а не меняем модель молча.
