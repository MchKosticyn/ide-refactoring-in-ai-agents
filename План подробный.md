## 1. Введение: термины ✅

**Время:** 1 мин.

**Слайд:** одна схема вместо списка. В центре — модель. Слева — контекст: «что модель видит» (системный промпт, история чата, прочитанные файлы, результаты вызовов). Справа — инструменты (tools, тулы): «что модель может вызвать» (чтение файла, поиск по тексту, правка файла, запуск тестов). Стрелка от инструментов обратно в контекст: результат вызова возвращается в контекст. Подпись: ИИ-агент — модель + контекст + инструменты, работает циклом.

**Говорим:**
- ИИ-агент — модель с инструментами. Читает и редактирует файлы, запускает сборку и тесты. Сама решает, какой инструмент вызвать следующим.
- Контекст — всё, что модель видит в момент генерации. Больше ничего она не видит.
- Инструмент — функция с текстовым описанием. Модель выбирает инструмент по этому описанию и по результатам предыдущих вызовов.
- Остальные термины — по ходу, когда понадобятся.

**Возврат после демо (пункт 2):** одна фраза — «агент из демо искал текстом и правил текстом; это и были его инструменты».

**Зачем:** закладывает мысль для пунктов 14–15: модель видит только контекст, поэтому описание тула и текст ошибки — единственное, по чему она принимает решение. Здесь это не проговариваем, только рисуем стрелку.

**Терминология:** на слайде «инструменты (tools, тулы)» — как в вебинарах; дальше в докладе говорим «тул».

**Не вводим здесь:** LSP, PSI, MCP.

## 2. Демо (видео) ✅

**Время:** 3 мин видео + 1 мин разбор.

**Кейс** — переименование метода в Java/Kotlin-проекте. Пять ловушек, каждая ломается по своей причине:
1. Перегрузка — в классе есть метод с целевым именем, но другой сигнатурой. После текстовой правки часть вызовов привяжется к нему. Сборка и тесты проходят, поведение другое.
2. Переопределение — Java-наследник. Агент может найти по подстроке, но связь с базовым методом не видит.
3. Kotlin-наследник — обращается к методу как к свойству (`obj.name`). Искомой подстроки в коде нет, текстовым поиском не находится в принципе.
4. Упоминание в строке лога — совпадение подстроки, править не надо. Агент правит.
5. Spring XML — имя метода/свойства в конфигурации. **Проверить руками до записи**, что IntelliJ видит связь Java ↔ XML (подтверждение есть только из блога 2006 года). Если не подтвердится — заменить рефлексией по строковому литералу.

**Слайд 1 — видео.** Слева область под видео, справа колонка «действия агента»: получает задачу → ищет вхождения по тексту → читает файлы → правит каждое место текстом → отдаёт diff. В титрах: агент, модель, дата прогона.

**Слайд 2 — разбор результата.** Три карточки:
- Пропущено — Kotlin-наследник. Сборка не проходит.
- Изменено лишнее — совпадение имени в другом классе и в строке лога. Сборка проходит.
- Изменено поведение — вызов привязался к другой перегрузке. Сборка и тесты проходят, поведение другое.
Вывод внизу: проблема не в модели, а в инструментах.

**Говорим:**
- Просим агента переименовать метод обычным способом — текстовыми правками.
- После видео: возврат к терминам — агент искал текстом и правил текстом, это были его инструменты.
- Три вида ошибок. Отдельно проговорить третий: сборка и тесты проходят, поведение изменилось — это к пункту 17.3.

**Формат:** только запись. Живьём современная модель может справиться, и проблема не будет поставлена. Перед конференцией прогнать на 2–3 моделях; если проходит — усилить кейс или оговорить: «на другой модели может пройти, но вероятностно, а не гарантированно».

**Зачем:** ставит проблему до теории. Третья карточка — единственный аргумент против «тесты спасут». Кейс возвращается в пунктах 8 (перегрузка), 18 и 19.

**Материалы:** `demo-spec.md`.

## 3. Рефакторинг — преобразование с гарантиями ✅

**Время:** 3 мин.

**Слайд:** определение сверху в рамке; две карточки подзадач; рамка «что / как» внизу.
- Верх: «Рефакторинг — изменение структуры кода без изменения поведения программы».
- Карточка 1: «Подзадача 1: найти все места». Нужна полнота. Подпись-пример: «200 вызовов × 99 % = 2 пропуска».
- Карточка 2: «Подзадача 2: выполнить». Нужна корректность: правка не должна менять привязку вызовов, видимость, иерархию переопределений.
- Низ: «Модель решает „что", детерминированный инструмент — „как"».

**Говорим:**
- Определение. Рефакторинг — не поиск и не генерация, а преобразование с гарантией сохранения поведения.
- Две подзадачи. Разные инструменты сильны в разных — половина споров «grep против IDE» из-за того, что сравнивают на разных подзадачах.
- Полнота: 99 % не годится. Числовой пример — 200 вызовов, два пропуска; если один из них перегрузка, тесты его не поймают (связь с демо).
- Корректность: что именно не должно измениться.
- Рамка: модель — что менять и зачем; детерминированный инструмент — как. Повторяется в пунктах 6 и 18.

**Не обсуждаем:** эмбеддинги / RAG — вне рамок доклада. Вопрос «зачем агент, если есть Shift+F6» — в Q&A, не в теле.

**Зачем:** каркас. Пункты 4–6 оцениваются по двум подзадачам, пункты 7–9 объясняют, откуда у движка полнота и корректность, пункт 10 сводит в таблицу.

## 4. Подход 1: текстовый подход ✅

**Название:** «Текстовый подход». Короткая форма для таблицы — «Текст». Три подхода различаются тем, чем для агента является код: текст / символы одного языка (LSP) / модель кода (движок IDE).

**Время:** 5 мин, три слайда (после демо и разбора).

### Слайд 0 — что из себя представляет подход

Схема цикла агента: задача → поиск по тексту (grep, ripgrep) → чтение найденных файлов → правка текстом → diff. Подпись: агент работает с кодом как с текстом, символов для него не существует; так устроено большинство агентов. Внизу — три механизма правки: скрипт / regex по файлам; тул «правка фрагмента» (удалить / добавить / заменить, список мест — из поиска); перезапись файла целиком.

### Слайд 1 — поиск (подзадача 1: полнота)

Две колонки + один код-фрагмент.
- «Плюсы» (зелёная): ноль настройки; любой язык; работает на некомпилирующемся коде.
- «Пределы» (красная): «имя» ≠ «символ» — одноимённые вхождения в другом классе, в комментариях и строках; «символ» ≠ «имя» — алиасы импорта, наследование, обращение через свойство; шум — частотные идентификаторы (run, config, init) дают сотни вхождений.
- Фрагмент — Kotlin-свойство из демо:
  ```kotlin
  val label = user.name   // вызов getName(), подстроки "getName" нет
  ```
- Подпись к шуму: «По данным исследования: 71–75 % провалов текстового поиска в агенте — не пропуски, а „нашли, но утонуло в шуме"».

**Говорим:**
- Как устроено: поиск по тексту, чтение файлов. Так устроено большинство агентов.
- Три плюса; последний вернётся в таблице как честная ниша подхода.
- Имя ≠ символ в обе стороны. Kotlin-свойство — подстроки нет в принципе. Ловушка 3 из демо.
- Шум: агент получает сотни вхождений и не может выбрать нужное. Контринтуитивно: главная беда не пропуски, а шум.
- **Где ломается полнота:** пропуски (символ без имени) и ложные попадания (имя без символа). Оба — из-за того, что подстрока не равна символу.

### Слайд 2 — правка (подзадача 2: корректность)

Три карточки по механизмам правки (сами механизмы уже названы на слайде 0 — здесь только где ломаются); внизу — вывод.

| Механизм | Что делает | Где ломается |
|---|---|---|
| Скрипт / regex по файлам | Заменяет подстроку везде, где нашёл | Правит строки и комментарии; не проверяет, что заменённое — тот самый символ |
| Тул «правка фрагмента» (удалить / добавить / заменить) | Модель сама перечисляет файлы и места, каждое — отдельный вызов | Каждое место — отдельный шанс промахнуться; список мест — из поиска со слайда 1 |
| Перезапись файла целиком | Модель генерирует новый файл | Помимо целевой правки может изменить соседний код; самый дорогой |

Вывод внизу: «Каждая правка — независимая текстовая операция без проверки результата. Ошибка не обнаруживается в момент применения».

**Говорим:**
- Поиск — половина дела; дальше агент применяет изменения, и делает это тоже текстом.
- Три механизма, у каждого свой провал.
- Общее: правка «прошла» всегда, даже если заменила не то. N мест — N независимых операций, и никакого сигнала об ошибке.
- **Где ломается корректность:** правка не знает, что она меняет — символ, строку или комментарий; не проверяет, к чему после правки привяжется вызов (перегрузка из демо); не является одной операцией — состояние «7 из 9» возможно.

**Зачем:** первый подход проваливает обе подзадачи, и это разные провалы. Слайд 2 готовит контраст с пунктом 8 (движок проверяет правку до применения) и пунктом 9 (одна команда, а не N независимых).

**Материалы:** цифра про шум — GrepRAG (arXiv 2601.23254), помечена [V] в `handoff-prompt-refactoring-talk.md`. Сверить перед слайдом.

## 5. Подход 2: LSP ✅

**Время:** ≈ 5,5 мин. Четыре слайда + видео. Сокращено: дата 2016 и механизм `j → i` — в заметки.

### Слайд 1 — что это и что даёт

- Определение: LSP (Language Server Protocol) — протокол между редактором и сервером языка. Отдельный процесс понимает язык; редактор или агент спрашивает его по стандартному протоколу. Один сервер — один язык.
- Схема: редактор/агент → запрос «переименуй символ здесь» → сервер языка → правка (список текстовых изменений) → применяет клиент.
- Что даёт: переход к определению, поиск использований, переименование по символу. Один протокол для всех языков: rust-analyzer, gopls, jdtls, tsserver.

**Говорим:** вводим термин здесь. Это первый подход, где есть понятие символа — полнота в пределах одного языка появляется. Важная деталь схемы, к которой вернёмся: сервер возвращает список текстовых правок, применяет их клиент.

### Слайд 1 — демо (видео) — TODO записать

Слайд: слева область под видео, справа колонка действий: F2 на объявлении → редактор отправляет запрос серверу → сервер ищет по символу → возвращает список правок → редактор применяет.

Тот же кейс из пункта 2 через VS Code + Java-сервер (jdtls).

Ожидаемый результат (проверить записью, не предсказывать):
- Java-вызовы, Java-override — переименованы.
- Kotlin-наследник — не переименован: сервер о Kotlin не знает.
- Строка лога — не тронута (лучше, чем текстовый подход).
- Spring XML — не тронут.
- Перегрузка — зависит от того, посчитает ли движок Eclipse затенение ошибкой или предупреждением. Если предупреждением — правка применится без сообщения.

Титры: редактор, сервер, версия, дата.

### Слайд 3 — разбор результата

Три карточки как после первого демо, по факту записи:
- Пропущено — Kotlin-наследник, Spring XML.
- Изменено лишнее — (ожидаемо пусто; отметить как плюс).
- Изменено поведение — перегрузка, если применилась без предупреждения.

**Говорим:** полнота в одном языке есть, за границей языка — нет. Конфликтов не показано. Контраст с первым демо: меньше лишнего, но пропуски те же, где нет символа для этого сервера.

### Слайд 4 — пределы протокола + пример

Четыре карточки:
1. **Конфликты невыразимы.** Запрос на переименование — документ, позиция и поле «новое имя». Ответ — готовая правка или ошибка строкой. Понятия конфликта в спецификации нет.
2. **Параметров у рефакторинга нет.** Code action — команда без параметров. Спецификация приводит «Add or remove parameter» как пример, но не даёт способа передать, какой параметр и куда.
3. **Атомарность не гарантируется.** Правка — список текстовых изменений, применяет клиент. Стратегия отката — декларация клиента, сервер повлиять не может. VS Code: транзакционно только для текста; при создании файла откат не гарантирован.
4. **Межъязыковой рефакторинг невозможен.** Отрабатывает движок одного языка. Клиент берёт ответ первого сервера, остальные не опрашивает. Java-сервер не знает о Kotlin.

Дополнительная строка под карточками (серым): «На некомпилирующемся коде сервер вправе отказать в переименовании (спецификация это разрешает; Go-сервер так делает); в ряде случаев переименование на коде с синтаксической ошибкой применяется неверно».

Пример к карточке 1 (отдельный слайд или врезка): `j → i` — затенение во вложенном классе, Java-сервер применяет правку без предупреждения.
```java
void m() {
  int i = 0;
  class B {
    int j;              // переименуем в i
    void k() { j = i; } // после правки: i = i
  }
}
```
На слайде под кодом — одна строка: «Движок нашёл конфликт. Протокол его не передал — правка применена без предупреждения».

Механизм — **только в заметках** (сокращено для тайминга): движок Eclipse вычислил конфликты с уровнями важности; LSP-обработчик прерывается только на «фатально»; функция сборки правки принимает только набор изменений — статус передать некуда.

**Говорим:**
- Четыре предела; по каждому — одна фраза.
- Оговорка: поведение сильно зависит от реализации конкретного сервера. Пределы протокола общие, но что сервер делает внутри них — своё у каждого: Go-сервер отказывает при ошибках компиляции и тщательно проверяет конфликты, Java-сервер применяет молча, Rust — 167 операций, Python в открытой части — почти ноль.
- На атомарности: **поиск у LSP — по символам, применение — текстовое, клиентом.** По подзадаче 1 LSP ближе к движку, по подзадаче 2 — к текстовому подходу.
- Пример `j → i`: сборка и тесты проходят, поведение изменилось. Движок посчитал — протокол не передал.
- Устно, без слайда: LSP не заменяет движок рефакторинга, а ограничивает доступ к нему. Java в VS Code — это Eclipse JDT под LSP; баги наследуются, диагностика теряется.

**Не на слайде, в заметках для Q&A:** цитаты авторов протокола («I am actually against this»), багрепорты 2024 («Renaming methods causes code behavior to change»), метка upstream от Red Hat, код клиента VS Code про «первый ответивший побеждает», три движка с непередаваемой возможностью (tsserver, rope, jdtls).

## 7. Полнота: откуда движок знает все места ✅

**Время:** 3 мин, один слайд (сравнение «текст / дерево» переехало в пункт 6, слайд «что это»).

### Слайд 1 — код как текст и код как дерево — перенесён в пункт 6

Один фрагмент кода дважды, слева и справа.
- Слева, «как видит текстовый поиск»: строки символов, подсвечены совпадения подстроки `getName` — включая строку лога и одноимённый метод другого класса.
- Справа, «как видит IDE»: дерево — файл → класс → метод → вызов → ссылка на объявление. Подсвечены узлы-ссылки на нужный метод; строка лога и чужой метод не подсвечены.
- Подпись: «PSI (Program Structure Interface) — модель кода, которую IDE держит в памяти и синхронизирует с редактором».

**Говорим:** вводим PSI. Одно и то же — два представления. Слева нет понятия символа, справа каждый вызов знает своё объявление. Дальше говорим «модель кода».

### Слайд 2 — ссылки и индексы

- Схема: объявление `getName()` слева; три стрелки-ссылки к нему от разных мест — вызов в Java, override в Kotlin, имя бина в Spring XML. Подпись под объявлением: «ссылка = источник → цель, и обратный поиск „кто на меня"».
- Зелёная карточка «Источники ссылок»: ссылка — отдельный от дерева слой, объект «источник → цель»; плагины добавляют ссылки в другие языки и конфигурацию; индексы — где какое имя встречается, кто кого наследует, поэтому обход быстрый; рефлексия по строковому литералу — тоже ссылка.
- Серая строка под карточкой: «Модель кода и индексы живут в памяти IDE и в кэшах на диске; строятся при индексации. На некомпилирующемся коде — частично: парсер восстанавливается, неразрешённые ссылки помечаются отдельно».
- Красная рамка «Ограничение», две строки моноширинным:
  `Class.forName("com.foo.Bar")` — ссылка есть, переименуется
  `Class.forName(prefix + name)` — runtime-рефлексия, не анализируется

**Говорим:**
- Ссылка — не часть дерева, а слой поверх. Поэтому любой плагин может добавить ссылку туда, где компилятор её не видит: Spring XML, аннотации, `.properties`, `getDeclaredMethod("getName")`. Отсюда полнота больше, чем у компилятора.
- Индексы — почему обход всех ссылок в большом проекте занимает секунды, а не минуты. Цена — индексация и кэши; подробнее в пункте 11.
- Некомпилирующийся код: модель строится, но часть ссылок не разрешается — они попадают в группу «динамические», рефакторинг применяется с оговоркой «не все использования переименованы».
- Ограничение: если имя вычисляется в runtime — ссылки нет. Движок этого не видит; никто не видит. Найденное, но недоказанное, помечается отдельно, а не правится молча.

**Зачем:** объясняет первую из трёх гарантий. Слайд 1 — для тех, кто PSI не знал; слайд 2 — механизм полноты и её граница. Граница проговаривается здесь, чтобы не всплыла вопросом в Q&A.

**Материалы:** `notes-lsp-vs-psi.md`, раздел 2.1 и раздел 3 («Что принципиально не видно»). Spring XML — [С], проверить руками (см. пункт 2).

## 8. Корректность: откуда движок знает, что не сломает ✅

**Время:** 3 мин, один слайд.

**Слайд:** схема сверху, пример из демо снизу.
- Верх, рамка: «Проверки „имя занято" недостаточно — движок проверяет правку до применения».
- Схема, четыре карточки со стрелками: **Копия вызова** (оригинал не трогаем) → **Новое имя** (на копии) → **Резолв заново** (какая перегрузка?) → **Другой метод?** (→ конфликт).
- Низ, пример из демо — ловушка 1, два состояния рядом:
  - слева: вызов до переименования, подпись «привязан к `getName(String)`»;
  - справа: тот же вызов после гипотетической правки, подпись «привязался бы к `getDisplayName(Object)` — другая перегрузка»;
  - между ними — текст конфликта движка: «После переименования будет вызван другой метод».

**Говорим:**
- «Имя занято» — проверка имени. Движку нужна проверка смысла: изменится ли, к чему привязан вызов.
- Механизм: копия выражения-вызова, на ней новое имя, повторное разрешение перегрузок. Если вызов привязался бы к другому методу — конфликт.
- Это ловушка из демо: текстовый подход применил и промолчал, LSP применил и промолчал, движок остановился до применения.
- Конфликт — не исключение, а элемент результата: что не так, где, из-за чего.

**Не обсуждаем:** кто принимает решение по конфликту (человек / модель) и как — вне рамок.

**Зачем:** вторая гарантия. Замыкается на демо (все три подхода на одной ловушке). Текст конфликта — эталон для пункта 15 (сообщения тула).

**Материалы:** `notes-lsp-vs-psi.md`, раздел 2.2 — механизм из `RenameJavaMethodProcessor` (копия выражения, `advancedResolve`), ключ сообщения `method.call.would.be.linked.to.0.after.rename`.

## 9. Атомарность: почему не бывает «наполовину» ✅

**Время:** 2 мин, один слайд.

**Слайд:** две карточки + врезка.
- Карточка 1 «Одна команда»: поиск использований, проверка конфликтов и правка — одна команда движка. Подпись: «как транзакция в БД: либо все правки, либо ни одной».
- Карточка 2 «Один откат»: глобальный откат на всю операцию, а не по файлу. Ctrl+Z один раз. Не бывает состояния «переименовано в семи файлах из девяти».
- Врезка внизу (фиолетовая): «Проверка актуальности: код изменился между поиском и применением → рефакторинг не применяется, поиск повторяется».

**Говорим:**
- Третья гарантия. Контраст с текстовым подходом из пункта 4: там N мест — N независимых операций без сигнала об ошибке; здесь одна операция, один результат.
- Аналогия с транзакцией — либо всё, либо ничего.
- Врезка: между фазой поиска и фазой применения код может измениться (сам пользователь, другой агент). Движок это отслеживает и не применяет устаревший план. Для агента это отдельное состояние результата — вернёмся в пункте 14.

**Зачем:** третья гарантия; закрывает блок 7–9. Проверка актуальности — задел для протокола preview → apply.

**Материалы:** `notes-lsp-vs-psi.md`, раздел 2.3. Строка из ресурсов IDE: «Cannot perform refactoring operation. There were changes in code after usages have been found. Please perform usage search again.»

1. Рефакторинг — преобразование с гарантиями: полнота при поиске мест, корректность при выполнении.
2. Проблема не в модели, а в инструментах: сильная LLM с текстовыми правками ошибается там, где слабая с движком — нет.
3. Гарантии даёт только модель кода: текст не знает символов, LSP знает их в одном языке и не передаёт конфликты, движок IDE знает всё и проверяет правку до применения.
4. Модель решает «что», детерминированный инструмент — «как». Не заставляйте LLM делать работу компилятора.
5. Движок рефакторинга IDE — готовое «как»: полнота, конфликты до правки, атомарность. Его можно отдать агенту.

**Говорим:** по тезису — одна фраза. Пятый — последним: доклад закрывается на решении, а не на принципе.

**Не включаем:** «ноль незамеченных пропусков» — деталь разбора демо, не главная мысль.

**Далее:** слайд «Спасибо» с контактами. Доклад заканчивается здесь.

## Q&A: заготовки ответов

### «Почему не сделать LSP как PSI?»

**Короткий ответ (со сцены):** PSI — не протокол, а общая модель кода в одном процессе. LSP по замыслу — один сервер на один язык, изолированные процессы, обмен только текстовыми правками. Чтобы Java-сервер увидел Kotlin-наследника, нужен либо один процесс с общей моделью — это и есть IDE, — либо протокол координации серверов, который авторы LSP официально признали вне области протокола в 2016 году и к которому не возвращались.

**Развёрнуто (если спросят дальше):** три препятствия по спецификации.
1. Нет типа для конфликтов и предупреждений. Ответ на переименование — правка или ошибка строкой. Запрос на протокол рефакторинга открыт с 2016 года.
2. Нет параметров у операций. Автор протокола на запрос «дайте серверу спросить у пользователя»: «a server shouldn't have the need to ask for additional input».
3. Клиент объединяет ответы нескольких серверов только для переименования файлов; для символов берёт первый непустой ответ.

**Честная оговорка:** спецификация формально не запрещает один сервер на много языков. Но тогда это IDE в другой упаковке — JetBrains ровно так и делает: Kotlin LSP собран на ядре IntelliJ и частично закрыт.

Источник: `notes-lsp-vs-psi.md`, разделы 1.1, 1.2, 1.5, 1.7, 1.11.

### «Зачем агент, если есть Shift+F6?»

Не в теле доклада (решение по пункту 3). Ответ: ценность не в одном переименовании, а когда рефакторинг нужно придумать («найди в модуле, что стоит выделить»), когда их двадцать связанных, или когда он часть большой задачи, куда пользователь не собирался лезть руками.

### «А эмбеддинги / RAG?»

Вне рамок доклада. Одна фраза: для поиска повода — да; для полноты и корректности — нет, потому что это ранжирование вероятных, а не перечисление всех.
