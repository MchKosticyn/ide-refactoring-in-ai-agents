# План доклада

1. Введение (термины)  
   1. Что такое агент, контекст, инструменты  
2. Демо (видео)  
   1. Проект: метод с перегрузкой, метод с переопределением, Kotlin-наследник, упоминание в строке лога, Spring XML  
   2. Просим агента переименовать метод обычным способом – текстовыми правками  
3. Рефакторинг – не поиск, а преобразование с гарантиями  
   1. Идея: меняем структуру, не меняем поведение  
   2. Модель решает “что”, детерминированный инструмент – “как”  
   3. Подзадача 1: найти все места – нужна полнота, 99% не годится  
   4. Подзадача 2: выполнить – нужна корректность  
4. Подход 1: текстовый поиск  
   1. Как выглядит внутри агента: поиск по тексту, чтение файлов, правка текстом  
   2. Чем подкупает: ноль настройки, любой язык, работает даже на некомпилирующемся коде  
   3. “Имя” не равно “символ”: вхождения в другом классе, вхождения в комментариях и строках, алиасы импорта, наследование, обращение через свойство  
   4. Проблема не только в пропусках, но и в лишнем шуме  
5. Подход 2: LSP  
   1. Что это: отдельный процесс понимает язык, редактор спрашивает его по стандартному протоколу  
   2. Что даёт: определение, использования, переименование по символу  
   3. Пределы  
      1. конфликты невыразимы  
      2. параметров у рефакторинга нет  
      3. атомарность  
      4. межъязыковой рефакторинг разом невозможен (отрабатывает движок только одного языка)  
6. Подход 3: движок рефакторинга IDE (IntelliJ)  
   1. Код представлен не текстом, а связанным графом символов  
   2. “Все использования” – обход ссылок, а не поиск подстроки  
   3. Три вещи, которых нет у остальных: полнота, конфликты до правки, атомарность  
7. Полнота: откуда движок знает все места  
   1. Модель кода, которую IDE держит в памяти (она же PSI)  
   2. Ссылка – отдельный от текста слой: источник, цель, обратный поиск  
   3. Индексы: где какое имя встречается, кто кого наследует  
   4. Ограничение: runtime рефлексия не анализируется  
8. Корректность: откуда движок знает, что не сломает  
   1. Проверки «имя занято» недостаточно  
   2. Движок проверяет правку: копия вызова, на ней новое имя, повторное разрешение перегрузок  
   3. Если вызов уехал бы на другой метод – конфликт. Это случай из вступительного демо  
   4. Конфликты приходят списком: что, где и из\-за чего, – дальше решает человек или модель: применить, сузить область, отказаться  
9. Атомарность: почему не бывает «наполовину»  
   1. Одна команда, один откат – глобальный, а не по файлу  
   2. Не бывает состояния «переименовано в семи файлах из девяти»  
   3. Если код изменился, то рефакторинг не применяется  
10. Таблица сравнения: полнота и корректность  
    1. Подходы (текстовый поиск, LSP, IDE) на двух осях (полнота, корректность)  
    2. Полнота: находит ли все затронутые места  
    3. Корректность: гарантирует ли сохранение поведения  
11. Цена и границы подхода  
    1. Нужна живая IDE с индексами и кэшами  
    2. Индексация занимает время, и в этот период рефакторинг недоступен  
    3. Применение правки блокирует запись  
    4. Сложности с worktree  
    5. Сложности работы на CI и удалённых машинах  
12. MCP для рефакторинга  
    1. Что такое MCP: способ дать агенту другие инструменты  
    2. Встроенный сервер IDEA – только переименование  
    3. Другие MCP-серверы для рефакторинга  
13. 12\. Адресация кода  
    1. Сложности модели с оффсетами  
    2. Что работает: FQN, сигнатура, …  
    3. Контрпример: адресация «путь плюс имя» неоднозначна на перегрузках  
    4. Отдельный тул поиска символа, возвращающий кандидатов с контекстом для выбора  
14. Гранулярность и проектирование тулов  
    1. 40 узких тулов забивают контекст, и модель путается  
    2. Один универсальный перекладывает схему в свободный текст, и модель врёт в параметрах  
    3. Описание тулов – промпт: когда применять, что ожидать  
    4. Ссылки на другие тулы, когда есть связки тулов (сначала запусти тот, потом этот)  
15. Ошибки тула как часть промпта  
    1. “Refactoring failed” – тупик  
    2. “Символ неоднозначен, вот кандидаты” – понятен следующий шаг  
    3. Хорошее сообщение говорит: что не так, где это произойдёт, из\-за чего  
    4. Сообщения проектируются так же тщательно, как описания тулов  
16. Грабли движка IntelliJ  
    1. Индексация  
    2. Потоки и транзакции: писать можно только в командах записи  
17. Советы пользователям агентов

    2. Рефакторинг – отдельным коммитом  
    3. Регрессионные тесты как фиксация поведения
