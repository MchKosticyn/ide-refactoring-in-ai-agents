# Материал для слайдов: движок IDE против остальных подходов

Заметки к докладу «Рефакторинг в ИИ-агентах». Это **не план**, а склад проверенных фактов и цитат под конкретные пункты плана.

Пометки достоверности:
- **[И]** — проверено по первоисточнику (спецификация, исходники, официальная документация, трекер).
- **[С]** — только из поискового сниппета, требует сверки перед слайдом.

Состояние на 2026-08-04. Часть фактов свежая (баги, обновлённые в последние дни) — **перед вёрсткой слайдов с дословными цитатами прогнать сверку заново**.

---

## 1. Для пункта «Подход: LSP»

### 1.1. Конфликты в протоколе невыразимы

- **[И]** Весь запрос на переименование — документ, позиция и одно поле `newName: string`. Никаких опций.
- **[И]** Ответ — либо готовая правка, либо ошибка со строкой. Третьей ветки «правка + предупреждения» в типе нет.
- **[И]** Слов «conflict» и «collision» во всей спецификации 3.18 — ноль совпадений.
- **[И]** Единственное, что похоже на предпросмотр — свободная строка-ярлык плюс булев флаг «нужно подтверждение». Ни уровня важности, ни машинно-читаемой категории, ни привязки к виновнику.
- **[И]** Спецификация 3.18 (последняя, датирована апрелем 2026) в списке нового по рефакторингу не содержит ничего, кроме одного булева флага «эта правка — рефакторинг».

### 1.2. Признания авторов протокола

- **[И]** Запрос «An operation for refactorings» — открыт с **2016 года**, до сих пор не закрыт. Автор LSP перечисляет три блокера, второй дословно: *«communication on sematic shift warnings. Refactoring should be semantic preserving. But sometimes the semantic shift is wanted and we need to let the user confirm this.»*
- **[И]** Он же, раньше: *«We started a discussion about how a refactoring protocol could look like but we haven't found a good way to spec that yet.»*
- **[И]** На запрос «дайте серверу спросить у пользователя параметр» — дословно: *«I am actually against this… a client needs to provide a reasonable set of input to a request and a server shouldn't have the need to ask for additional input.»*
- **[И]** Запрос «Signal the client a refactoring failed» — открыт с 2024, ноль комментариев. В теле: *«the client has no info to correlate an incoming showMessage with a previously launched refactoring.»*

### 1.3. Убойный слайд: Java-сервер выбрасывает результат проверок

Три шага, каждый проверен по исходникам обработчика переименования в Java-сервере:

1. **[И]** Движок Eclipse выполняет **полную** проверку условий и формирует полноценный статус со всеми записями и уровнями важности.
2. **[И]** Порог прерывания выставлен на «фатально». Уровни «информация», «предупреждение» и **«ошибка» проходят молча**.
3. **[И]** Функция, превращающая результат в LSP-правку, принимает **только сам набор изменений** — статус в неё не передаётся. Перегрузки со статусом не существует. Донести предупреждение **структурно невозможно**.

Тот же паттерн в обработчике смены сигнатуры: полный статус уходит **в лог сервера**, пользователю достаётся одна строка.

**Репро на шести строках** (из открытого багрепорта, 2024):

```java
void m() {
  int i = 0;
  class B {
    int j;                  // переименовываем j -> i
    void k() { j = i; }     // становится i = i
  }
}
```

**[И]** Кластер багрепортов 2024 года, все открыты, с заголовками буквально: «Renaming methods causes code behavior to change», «Renaming fields causes naming conflicts between fields, missing check warnings», «Rename method refactoring causes a normal method in a subclass to be converted to a method in an inherited parent class». В поле «ожидаемый результат» дословно: *«When naming conflicts occur between fields, a warning should be given»*.

**[И]** На одном из них Red Hat поставили метку **upstream** — то есть сами признали, что баг в движке Eclipse, а не в LSP-слое.

**Пуант слайда:** движок всё посчитал правильно. Данные были. Их выбросили, потому что в протоколе нет поля.

### 1.4. Симметричный контраст: Kotlin-сервер деградирует в другую сторону

**[И]** Kotlin LSP от JetBrains конфликты собирает (в тот же тип коллекции, что и IDE) и при любом непустом наборе **бросает исключение** — правка не применяется вообще.

| | Java-сервер | Kotlin-сервер |
|---|---|---|
| Проверка конфликтов | выполняется | выполняется |
| Порог прерывания | только «фатально» | любой непустой набор |
| «Ошибка» / «предупреждение» | игнорируются, правка применяется | правка не применяется |
| Что видит пользователь | ничего | ошибка со склейкой строк |

В самой IDE это диалог «Обнаружены проблемы» с кнопкой «Всё равно применить». **В LSP такой диалог выразить нечем — обе реализации деградируют, просто в противоположные стороны: одна в «молча сломать», другая в «молча отказать».**

### 1.5. Рефакторингу нельзя передать параметры

- **[И]** Code action — непрозрачная тройка «заголовок, вид, готовая правка или команда». Параметров нет. Единственная лазейка — массив аргументов команды, содержимое которого спецификацией не описано вообще.
- **[И]** Ирония для сцены: спецификация приводит **«Add or remove parameter»** как пример вида рефакторинга — и не даёт ни одного способа сказать, *какой* параметр, *куда* и *с каким значением по умолчанию*.
- **[И]** Смены сигнатуры в протоколе нет. Из серверов она есть только у Java-сервера, и то через **отдельную панель в расширении редактора**, потому что через LSP параметры не выразить. У Rust — нет. В TypeScript запрос на переупорядочивание параметров открыт **с 2014 года**.
- **[И]** Три разных велосипеда в обход протокола: Java-сервер завёл **собственные RPC-методы вне спецификации**; TypeScript-сервер требует, чтобы клиент **сам** реализовал выбор файла (два года три месяца работы — на передачу одной строки с путём, и в документации дословно: *«requires custom implementation in the client»*); Go-сервер добавил диалоги, которые сам в релизноутах называет *«a non-standard feature of LSP»*.
- **[И]** Go-сервер о собственном обходе для смены сигнатуры: *«a very hacky workaround»*, *«just a temporary stopgap»*, с ограничением *«The new signature must have the same parameters»*.

### 1.6. Атомарности нет

- **[И]** Стратегия обработки сбоя — это **декларация клиента о себе**. Сервер её только читает; потребовать транзакционность не может, проверить правдивость — тоже.
- **[И]** VS Code объявляет «транзакционно только для текста». По определению спецификации это значит: как только в правке появляется создание, переименование или удаление файла, гарантия деградирует до «прервать, уже применённое оставить на диске».
- Это ровно интересные рефакторинги: перенос в другой файл, извлечение в новый файл, перенос класса в другой пакет, переименование Java-класса (влечёт переименование файла).
- **[И]** «Конфликт» в VS Code означает только «файл изменился с момента расчёта правки». Семантических конфликтов клиент не проверяет и проверить не может — у него нет модели языка. А сервер о них сообщить не может. Между этими двумя фактами и находится дыра.

### 1.7. Межъязыковой рефакторинг невозможен — и доказывается кодом клиента

- **[И]** В VS Code провайдеры переименования перебираются по порядку, и **первый непустой ответ побеждает** — остальных даже не спрашивают. Результаты не суммируются никогда. То есть даже поставив рядом Java-сервер и Kotlin-сервер, вы получите правку только от одного.
- **[И]** Красивая асимметрия: переименование **файла** может быть многосерверным (правки участников склеиваются, best-effort, с таймаутом и правом клиента их выбросить). Переименование **символа** — принципиально односерверное. Это объясняет, почему переименование класса иногда «почти работает», а метода — нет.
- **[И]** Координация серверов официально объявлена вне области протокола ещё в 2016-м: *«I agree that this shouldn't be speced in the LSP»*. Обещанных вместо этого рекомендаций за 10 лет не появилось. Запрос закрыт ботом: *«we don't plan to address it in the foreseeable future»*. Новый запрос «Cross server communication» открыт с конца 2024-го, ответа мейнтейнеров нет.
- **[И]** Инженер JetBrains в трекере Kotlin LSP: *«those are two separate LSP, and as far as I know, RedHat Java LSP does not know anything about Kotlin.»*
- **[И]** Матрица для Java + Kotlin под LSP:

| Сценарий | Работает? |
|---|---|
| Переименование в Kotlin → правит Kotlin | да |
| Переименование в Kotlin → правит вызовы в Java | **нет** |
| Переименование в Java силами Kotlin-сервера | **нет, провайдера не существует** |
| Переименование в Java через Java-сервер → правит Kotlin | **нет** |
| Переход к определению из Kotlin в Java | да (починено весной 2026) |
| Разрешение ссылки из Java в Kotlin | **нет** |

- **[И]** Тонкость, чтобы не ошибиться: с июля 2026 Kotlin-сервер **читает** `.java`-файлы (чтобы разрешать ссылки из Kotlin), но не рефакторит их. Формулировка: «читает Java, но не рефакторит».

### 1.8. Инъекция языков

- **[И]** В спецификации 3.18 нет ни одного упоминания инъекции, встроенных языков или виртуальных документов. Нет способа сказать «символы с 42 по 87 в этом строковом литерале — это SQL».
- **[И]** Официальный гайд VS Code по встроенным языкам предлагает два обхода, оба вне LSP, и про наш случай говорит дословно: *«For renaming, it can be challenging to make it work across different regions within different documents.»*
- **[И]** Идеальный практический пример — из трекера **самой команды Spring**, открыт с 2020 года: аннотация с ключом кеша, ссылающимся на поле через выражение в строке. Переименовали поле — всё скомпилировалось, тесты прошли, инвалидация кеша молча перестала работать. Дословно: *«it is hard to notice that the @CacheEvict does not work anymore as expected»*.

### 1.9. Лучший аргумент: возможность есть в движке, но передать её нечем

Это доказывает, что проблема не в лени реализаторов — один и тот же разрыв на трёх независимых движках:

- **[И]** TypeScript-движок умеет искать в комментариях и строках. **VS Code эти флаги хардкодит в `false`.**
- **[И]** Python-движок Rope умеет переименовывать в комментариях и строках, и даже внутри вычисляемого кода. Через LSP этот параметр передать нечем.
- **[И]** Java-сервер имеет флаг для текстовых вхождений и **не передаёт его никогда**, это не конфигурируется — при том, что в Eclipse IDE это обычная галочка в диалоге.

### 1.10. LSP наследует движок, а не отменяет его

**[И]** Java в VS Code построена на Eclipse JDT — подтверждено на четырёх независимых уровнях: README проекта, список зависимостей модуля, целевая платформа сборки (тянет модули прямо из репозиториев Eclipse) и **прямая копипаста** — в заголовке файла обработчика переименования стоит «Originally copied from org.eclipse.jdt.ui.refactoring.RenameSupport», а импорты — целиком внутренние, непубличные классы Eclipse IDE.

Вывод для доклада: **LSP не заменил движок — он надел на него узкое горлышко.** Метка upstream на баге и потеря статуса конфликтов — две стороны одной медали: баги наследуются, а компенсирующая их диагностика теряется.

### 1.11. Что реально есть в серверах (август 2026)

- **[И]** Rust — 167 операций, больше всех. Но: смены сигнатуры нет; переименование отказывается работать в макросах (в документации к коду авторов про это дословно **«Our current behavior is ¯\\_(ツ)_/¯»**); предупреждение о затенении реализовано через **фиктивную правку с текстовой аннотацией**, и автор изменения пишет: *«I'm not a fond of this approach, but I don't think LSP has a better way»*; конфликты имён между пространствами имён не детектируются — открытый, документированный способ сломать компиляцию переименованием.
- **[И]** Go — около 25 операций, но переименование самое серьёзное: *«takes great care to detect situations in which renaming might introduce a compilation error»*, *«should never introduce a compilation error, but it may introduce dynamic errors»*, и честное *«There is no substitute for good judgment and testing»*. Обновляет ссылки в документационных комментариях и файле модуля. Не обновляет теги структур и шаблоны.
- **[И]** Java-сервер — переименование пакетов **отключено с 2019 года** с комментарием в коде «not fully supported yet». Переименование метода **молча пропускает переопределения** — багрепорт открыт с 2018 года, почти 8 лет, с метками «баг» и «регрессия».
- **[И]** Kotlin-сервер (JetBrains) — с весны 2026 статус **альфа** (не pre-alpha, это устарело), частично закрытый исходный код. Из рефакторингов заявлено **только переименование**. Извлечения, встраивания, смены сигнатуры нет как классов.
- **[И]** Python в открытой части — почти ноль. Основной сервер официально: *«We have no plans to add additional language server features»*, рефакторинги живут в закрытом продукте, лицензированном **только для сборок Microsoft**. У второго сервера встроенное переименование **удалено** в 2024-м, а то, что осталось, возвращает правку как **полную замену всего файла**.

## 2. Для трёх пунктов о гарантиях движка

### 2.1. Полнота: ссылка как отдельный слой

- **[И]** Ссылка — **не** элемент синтаксического дерева. У неё есть источник и цель, и разрешение цели отделено от разбора текста; легально возвращает «не знаю».
- **[И]** Любой плагин может **дописать ссылки в чужой язык** через регистрацию поставщика ссылок на шаблон элементов. Отсюда движок видит связи, которых нет ни в грамматике, ни в байткоде.
- **[И]** Конкретные примеры в исходниках: **рефлексия по строковому литералу** (шаблоны для `Class.forName`, `ClassLoader.loadClass`, `getDeclaredField`, `getDeclaredMethod`, фабрики атомарных обновляторов полей); ссылки из строкового литерала в `.properties`; ссылки в XML-виде properties; FXML; ссылки внутри инъекций.
- **[И]** Учебный пример из официального туториала SDK ровно про это: плагин регистрирует ссылки на Java-литералы, и после этого «rename refactoring becomes reachable from definition and usages».
- **[И]** Сам поиск использований тоже расширяемая точка — именно сюда встраиваются другие языки.
- **[С]** Spring XML: подтверждение только из блога JetBrains **2006 года** (Find Usages на сеттере находит объявление свойства в XML; Safe Delete учитывает определения бинов). Актуальная справка об этом молчит, плагин закрыт, по исходникам не проверяемо. **На сцене показывать демо, а не ссылку.**

### 2.2. Корректность: движок примеряет правку до применения

Самое сильное место во всём исследовании.

**[И]** При переименовании метода движок **не проверяет «имя занято»**. Он берёт копию каждого вызова, применяет к копии новое имя и заново прогоняет разрешение перегрузок. Если вызов после правки привязался бы к **другому** методу — поднимается конфликт с текстом «после переименования будет вызван другой метод».

То есть проверяется не идентификатор, а **результат семантического разрешения в гипотетическом мире после правки**. Ни текст, ни LSP такого не выражают вообще.

**[И]** Реальные тексты конфликтов из ресурсов (готовая библиотека хороших сообщений об ошибках):

Переименование:
- «после переименования будет вызван другой метод»
- «X скроет переименованный Y», «X переопределит переименованный Y»
- «переименованный класс скроет X в Y», «переименованное поле скроет X»
- «метод скроет X родительского типа», «поле X скроет поле Y базового типа»
- «элемент с таким именем уже существует»
- «в Y уже есть X, он конфликтует с переименованным параметром»

Перенос и видимость:
- «X, используемый в Y, станет недоступен в модуле Z»
- «X имеет видимость Y и будет недоступен из Z»
- «X скрыл бы Y, который используется перенесённым Z»
- «перенос X из модуля Y в модуль Z может скрыть доступ к нему»

Подъём и спуск членов:
- «X в родительском классе столкнулся бы с методом Z из Y»
- «X использует Y, недоступный из родительского класса»
- «X уже переопределён в Y, метод не будет спущен в этот класс»
- «X унаследует несвязанные реализации по умолчанию из Y и Z»

Встраивание и извлечение:
- «X станет недоступен, когда Y будет встроен в Z»
- «метод с такой же сигнатурой уже существует»
- «переменная с именем X уже определена в выбранной области»
- «уже есть X, который был бы скрыт сгенерированным аксессором»

### 2.3. Атомарность и устаревание плана

- **[И]** Всё идёт **одной командой**: команда процессора, глобальный (а не по файлу) Undo, запись в локальную историю, регистрация отменяемого действия. Правка выполняется одним действием записи с прогрессом.
- **[И]** Отдельно ценное для агентов: движок отслеживает, что код изменился **между фазой поиска и фазой применения**, и отказывается применять устаревший план — «Cannot perform refactoring operation. There were changes in code after usages have been found. Please perform usage search again.»
- **[И]** Два **разных** экрана, которые часто путают:
  1. **Предпросмотр рефакторинга** — список мест в отдельной панели, откуда можно исключить пункты, затем кнопка «Применить».
  2. **Диалог конфликтов** — появляется при обнаруженных проблемах, с кнопками «Всё равно применить» и «Открыть в панели поиска».

Это референсная модель для протокола тулы: не два состояния, а **три** — «вот что будет», «вот проблемы, решай», «план устарел, пересчитай».

## 3. Для пункта «Цена и границы подхода»

### Операционная цена

- **[И]** Применение правки требует **потока UI и блокировки записи** — это не библиотечный вызов, который можно сделать из любого треда.
- **[И]** Безголовый запуск отдельно ограничен в правах: стартер приложения «may not directly change the PSI/VFS/project model of the opened projects, open new projects, or perform activities that mandate write-safe contexts».
- **[И]** Официальный CLI умеет ровно пять вещей: сравнение, слияние, форматирование, инспекции, установку плагинов. **Ни одной команды рефакторинга.** Инспекции умеют только отчёт, без применения фиксов, и не работают, если уже запущен другой экземпляр IDE.
- **[И]** Индексация — «a potentially lengthy process», во время которой доступны только фичи, не требующие индексов. Обращение к индексу в этот период — исключение.
- **[И]** Проверенная строка из ресурсов: **«Safe delete refactoring is not available during the project analysis»** — то есть недоступность рефакторинга в период индексации не догадка, а заявленное поведение.
- **[И]** Косвенное, но красноречивое: «dumb-совместимым» специально сделано только переименование **файла** — для этого есть отдельный процессор.
- **[И]** Требования к памяти: конкретного числа в документации нет вообще — «depends on the platform». IDE сама предупреждает, когда после сборки мусора свободно меньше 5% кучи.

### Что принципиально не видно

- **[И]** **Вычисляемая рефлексия.** Шаблоны поставщика ссылок начинаются с «строковый литерал»: `Class.forName("com.foo.Bar")` — ссылка есть, `Class.forName(prefix + name)` — ссылки нет. Идеальный слайд «сила и граница в одной строке исходника».
- **[И]** **Имена, собранные конкатенацией.** Поставщик вычисляет константное значение выражения; если это не строка — ссылок нет.
- **[И]** **Инъекции с невычислимым содержимым.** Платформа сама помечает такие «франкенштейн-инъекциями», с документацией: файл «should not be checked for errors at all, because the contents of the injections could not be evaluated completely at compile time». Это самопризнание платформы, а не наш вывод.
- **[И]** Найденное иногда честно помечается «не тронем»: «вхождения в комментариях, строках и не-кодовых файлах: N. Эти вхождения изменены не будут», «использование X в сгенерированном коде, которое небезопасно удалять».
- **[И]** Языковые границы признаются в текстах конфликтов: «X переопределён средствами Y. Этот язык не поддерживает рефакторинг Introduce Parameter Object».
- **[И]** Честная граница внутри мощного рефакторинга: конверсия «массив ↔ коллекция» в Type Migration сделана **рукописным конечным списком шаблонов** (`.length` → `.size()`, `Arrays.sort` → `Collections.sort`, и так далее). Никакого понимания семантики там нет.

## 5. Для пункта «Адресация»

- **[И]** Живой пример для контраста: официальный MCP-тул переименования адресует символ парой «путь в проекте + имя символа». На перегрузках такая адресация **неоднозначна** — а перегрузка уже есть в демо-кейсе.
- **[И]** У самой платформы «динамическая» ссылка — это ровно та, которая **не разрешается**. Такие использования попадают в отдельную третью группу дерева результатов: «В коде» / «В строках, комментариях и тексте» / **«Динамические»**. Готовый слайд про честность: движок не молчит про недоказанное, он это отдельно помечает.
- **[И]** То, что не удалось переименовать, показывается явно: «Не все использования были переименованы», «Следующие использования были безопасно пропущены: …».

## 6. Для пункта «Гранулярность и проектирование тулов»

### Как гранулярность решена в реальном движке

**[И]** Переименование — это **один** рефакторинг, а не 28 отдельных. При этом за ним стоят **28 подключаемых автопереименователей** (полный список получен обходом всех конфигураций репозитория, регистрации ровно в 9 файлах): аксессоры, перегрузки, наследники, тесты, тестовые методы, параметры в иерархии, параметры конструктора по полю, связанные файлы, переменные по имени типа, привязанные UI-формы, ресурсные бандлы и так далее.

Три вывода, применимых к дизайну тулов:

1. **[И]** Набор доступных опций **вычисляется анализом кода под модальным прогрессом** («Finding auto rename options»), а не задан статически. IDE сначала выясняет, есть ли вообще перегрузки, наследники, тесты и аксессоры, и только потом рисует галочки.
2. **[И]** Автопереименователи **без галочки применяются всегда** и общаются с пользователем только через отдельный диалог. То есть часть поведения не выставлена в интерфейс сознательно.
3. **[И]** Дефолты **разные по видам элементов**: поиск в комментариях по умолчанию включён только для переменных; поиск в тексте — для пакетов, классов и переменных. Один флаг с одним дефолтом был бы неверен.

### Контрпример: сколько параметров у настоящего рефакторинга

**[И]** Смена сигнатуры — это не «поменяй сигнатуру»:
- значение по умолчанию для нового параметра, подставляемое во все вызовы;
- режим «вместо литерала найти рядом с каждым вызовом переменную подходящего типа»;
- «не трогать вызовы, а сгенерировать перегрузку со старой сигнатурой, делегирующую в новую»;
- протаскивание нового параметра вверх по вызывающим методам;
- протаскивание нового исключения вниз, в переопределения подклассов.

**[И]** Ещё пример «движок понимает семантику»: извлечение функционального параметра анализирует фрагмент, выводит нужную сигнатуру, **ищет функциональные интерфейсы, подходящие под эту сигнатуру**, и оборачивает фрагмент. Предлагаются только интерфейсы с соответствующей аннотацией или из известных библиотек.

Вывод для слайда: мало тулов, богатые параметры, а набор доступных опций **считается, а не хардкодится**.

## 8. Для советов пользователям

- **[И]** Нет предпросмотра — нет и проверки конфликтов. Это надёжный внешний признак.
- **[И]** В результатах смотреть группы «в строках и комментариях» и «динамические» — движок сам помечает то, что не смог доказать.
- **[И]** Галочки в диалоге переименования не декоративны, и дефолты у них разные для полей, методов и переменных — от них зависит, тронутся ли комментарии, строки и конфиги.
- **[И]** Безопасное удаление различает **три** степени небезопасности с разными сообщениями: небезопасное использование в коде; в строке, комментарии или не-кодовом файле; в сгенерированном коде. Не-кодовые вхождения **никогда не удаляются автоматически**.

## 9. Ловушки: чего НЕ говорить со сцены

Проверено, что этого не существует, хотя оно ходит по статьям:

1. **Классов** `RenameFieldProcessor` (в Java), `JavaRenameRefactoringDialog`, `SafeDeleteImportStatementUsageInfo`, `ArrayListToLinkedListDescriptor` в репозитории **нет**. Поля, локальные и параметры обрабатывает один процессор переменных.
2. **Строки** «dynamic references will not be renamed» в ресурсах **нет**. Правильная формулировка — через группу «Динамические» (раздел 5).
3. Ядро Type Migration **переехало** в другой модуль — старые пути из статей неверны.
4. Отдельного рефакторинга **Replace Temp With Query** в IDEA нет, соответствующая страница справки отдаёт 404.
5. «Java-сервер не переименовывает геттеры и сеттеры» — **неверно**, они жёстко включены. Верный тезис: не обновляются **текстовые вхождения в комментариях и строках**.
6. «Kotlin LSP — pre-alpha» — **устарело**, с весны 2026 альфа.
7. «Спецификация LSP запрещает мультиязычный сервер» — формально **неверно**. Ограничение в том, что возможности сервера объявляются глобально, без привязки к языку, и в клиенте нет слияния результатов.
8. «Go-сервер откажется переименовать экспортируемый символ, используемый другим модулем» — **неверно**. Отказ только если переименование делает символ неэкспортируемым.
9. Багрепорт «Find and rename symbols with Spring» как доказательство **не использовать** — автор закрыл его сам со словами «some misconfiguration by my side».
10. Отсутствие багрепортов про «переименование не обновило Spring XML» — это **не** доказательство, что всё работает. Скорее пользователи этого не ожидают и не репортят. Показывать демо.
